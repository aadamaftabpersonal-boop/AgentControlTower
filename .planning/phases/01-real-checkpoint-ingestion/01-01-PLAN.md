## The D-01 / D-02 conflict, resolved (read this before writing any code)

`01-CONTEXT.md` flags an unresolved conflict between D-01 and D-02 and requires the planner to settle it explicitly. It is settled here, and the resolution is a **first-class field on the model**, not an ad-hoc special case at a call site.

**The facts, from the CLI source (read-only reference):**

- `pendingCheckpointJSON` (`cmd/entire/cli/checkpoint_list.go:27-38`) has field `condensation_id` marked `omitempty`, and its own doc comment states: *"CondensationID carries the checkpoint ID (PendingCheckpoint.CheckpointID) for logs-only points; it is empty for shadow-branch (uncommitted) points."*
- `entire checkpoint explain <id> --json` requires a resolvable checkpoint ID. A live shadow-branch entry has none yet.

**Resolution — two tiers, keyed on one predicate:**

| Pending entry | `condensation_id` | Enrichment | `detail_level` | `evidence_status` |
|---|---|---|---|---|
| Live shadow-branch (uncommitted) | empty / absent | **never called** | `list_only` | `OK` |
| Logs-only / already condensed | non-empty | `explain <condensation_id> --json` | `enriched` | `OK`, or `INSUFFICIENT EVIDENCE` if the envelope reports `partial` or a session `error` |

A `list_only` checkpoint is **`OK`, not `INSUFFICIENT EVIDENCE`**. Its list-level fields are complete and true; only the *detail* is not yet derivable, and that absence is stated by `detail_level` and by `unavailable_fields`. Reserving `INSUFFICIENT EVIDENCE` for records where expected data is genuinely missing or broken keeps the signal meaningful — if the normal live case were flagged as insufficient evidence, the dashboard would show a permanent warning for the ordinary state and the flag would carry no information.

**Corollary for the model:** `transcript`, `tool_calls`, and `commits` (named in INGEST-02's tech-spec field list) are **not derivable from either `--pending` or `explain --json`** — the export envelope is metadata-only by design (`checkpointExportJSON` doc comment: *"no schema invention, no transcript bytes"*). They are therefore never fabricated and never silently omitted: they are listed by name in `Checkpoint.unavailable_fields`. Per D-02, the tech spec is directional; per the PRD's honest-uncertainty principle, a field we cannot source is named as unsourced rather than emitted as `null` and read downstream as "empty".
</decision_conflict_resolution>
