## Backend Testing

- **Framework:** pytest ≥8.3, via `fastapi.testclient.TestClient` (backed by `httpx`).
- **Location:** `agent-control-tower/backend/tests/`
- **Config:** `pyproject.toml` → `[tool.pytest.ini_options] testpaths = ["tests"]`
- **Run command:** `cd agent-control-tower/backend && python -m pytest` (per README) — **verified working**: `6 passed, 1 warning in 0.44s` when run directly in this environment.

### Test files

1. **`test_health.py`** (2 tests)
   - `test_health_ok` — asserts `GET /health` returns 200, `status == "ok"`, and a `repo_root` key is present. Does not assert the exact `repo_root` value (correctly, since it varies per environment).
   - `test_version` — asserts `GET /version` returns 200 and `version == "0.1.0"`.
   - Neither test touches `entire_client` — these two endpoints have zero external dependency, which is exactly why they pass reliably in any environment (including this one, which lacks the `entire` binary).

2. **`test_entire_client.py`** (4 tests) — all use `monkeypatch` to avoid any real subprocess execution:
   - `test_run_json_decodes_stdout` — patches `subprocess.run` to return a fake `CompletedProcess`, asserts JSON decoding works and that the invoked args start with `settings.entire_bin` and end with `"--json"`.
   - `test_run_json_raises_on_nonzero_exit` — patches `subprocess.run` to return returncode 1, asserts `EntireCommandError` is raised.
   - `test_list_checkpoints_unwraps_dict_shape` — patches `entire_client.run_json` directly (one layer up), asserts the dict-shape response (`{"checkpoints": [...]}`) is unwrapped to just the list.
   - `test_list_checkpoints_passes_through_list_shape` — same but asserts a bare-list response passes through unchanged.

### Coverage gaps observed

- **No test for the `/api/checkpoints` route itself** — only the underlying `entire_client` functions are tested. There's no test using `TestClient` + a monkeypatched `entire_client.list_checkpoints` to verify the route wires the two together correctly, and no test covering what HTTP response `/api/checkpoints` produces when `EntireCommandError` is raised (currently: an unhandled 500, per live testing done in this session — see CONCERNS.md).
- **No test for `status()`** in `entire_client.py` — only `run_json` and `list_checkpoints` have direct test coverage; `status()` is untested despite being implemented.
- **No integration test that actually shells out to a real `entire` binary** — reasonable for CI portability, but means the "does this actually work end-to-end" question (asked live in this session) can only be answered by manual smoke-testing, not by the test suite itself.

## Frontend Testing

## Test Strategy Recommendation (given V0 status)

Per the hackathon build map's "Definition of Done for Every Version": *"tests cover important failure modes."* For V1 (real checkpoint ingestion), recommend adding:
1. A `TestClient`-based test for `/api/checkpoints` that monkeypatches `entire_client.list_checkpoints` (mirrors the existing pattern) to verify the route → client wiring, plus a case asserting the route's behavior when `list_checkpoints` raises `EntireCommandError` (this will force deciding on the currently-missing error-to-HTTP-status translation).
2. A frontend test framework choice (Vitest pairs naturally with Vite) before any product components land, so component-level tests aren't retrofitted later.
