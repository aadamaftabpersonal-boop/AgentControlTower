# CONVENTIONS

**Analysis Date:** 2026-09-06

Scope: `agent-control-tower/` (the hackathon product). The root Go CLI has its own extensively documented conventions in the root `CLAUDE.md` (root anchors, error-handling via `SilentError`, git safety rules, etc.) — those are a separate, much larger convention set for a codebase this project does not modify.

## Backend (Python)

### Style
- Type hints used throughout function signatures (`def health() -> dict`, `def run_json(args: list[str]) -> dict | list`).
- Modern Python union syntax (`dict | list`) — confirms Python 3.11+ target, matches `requires-python = ">=3.11"`.
- Module-level docstrings explain *why*, not *what* — e.g. `entire_client.py`'s docstring states the single-chokepoint rationale rather than restating the code.
- No comments inside function bodies — self-documenting via naming (`EntireCommandError`, `run_json`, `list_checkpoints`).

### Error Handling
- Custom exception class pattern: `EntireCommandError(RuntimeError)` carries structured context (`args_`, `returncode`, `stderr`) rather than just a formatted string, so callers can inspect specifics (`entire_client.py:15-20`). Note the trailing underscore on `self.args_` — avoids shadowing the exception base's inherited `args` attribute.
- Errors raised at the boundary (inside `run_json`) rather than swallowed — the wrapper functions (`list_checkpoints`, `status`) do not catch/handle `EntireCommandError`; it propagates to the FastAPI route, which (at V0) has no exception handler, so it surfaces as a generic 500. **This is the actual cause of the `/api/checkpoints` 500 observed when `entire` isn't installed** — there's no try/except translating `EntireCommandError` into a structured HTTP error response yet.

### Configuration
- Settings-as-singleton-object pattern, instantiated at import time (`settings = Settings()` at module bottom of `config.py`), not passed via FastAPI's `Depends()` dependency injection — a simpler pattern appropriate for a single-tenant local tool, but means settings can't be overridden per-request/per-test without monkeypatching the module attribute (which is exactly what the test suite does — see TESTING.md).
- Environment-variable-driven, with explicit defaults documented in a docstring (`config.py:8-12`) rather than a separate config-schema doc.

### Testing conventions
- `monkeypatch.setattr` used to substitute both `subprocess.run` (for `run_json` tests) and `entire_client.run_json` itself (for the wrapper-function tests `test_list_checkpoints_*`) — layered testing, each function tested against its immediate dependency rather than the whole chain.
- Fake functions defined inline in each test (`def fake_run(args, cwd, capture_output, text, timeout): ...`) rather than a shared fixture/mock library — keeps each test self-contained and readable at the cost of some duplication (4 lines each × 2 tests). Given the small scope this is a reasonable tradeoff, not yet worth extracting a fixture.

## Frontend (TypeScript/React)

- Currently unmodified Vite scaffold — no product-specific conventions have been established yet (functional components with hooks is the only pattern present, via `App.tsx`'s `useState`).
- TypeScript strict-mode config inherited from Vite's template (`tsconfig.app.json`) — not yet exercised beyond the starter component.
- `oxlint` is the configured linter (not ESLint) — faster Rust-based linter; `.oxlintrc.json` present but default/minimal.

## Documentation Conventions

- Product README (`agent-control-tower/README.md`) explicitly states current version status at the bottom ("## Version status") rather than in a separate CHANGELOG — a lightweight single-source-of-truth pattern appropriate for a fast-moving hackathon project. Recommend keeping this pattern updated at each version milestone (V0 → V1 → ...) since the hackathon doc stack's `10_VERSION_ROADMAP.md` is the authoritative version list but lives in a zip, not in-repo as a live doc.

## Commit Conventions

- Root repo's `CLAUDE.md` mandates `mise run check` (fmt+lint+test:ci) before every commit — this applies to the Go CLI only. `agent-control-tower/` has no equivalent documented pre-commit gate yet; recommend adding one (e.g. `cd backend && python -m pytest && cd ../frontend && npm run build`) if/when this project adds CI or a commit hook, since currently correctness is verified manually per the README's "Testing" section.
